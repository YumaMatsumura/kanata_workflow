# KANATA audit

改善候補を読み取りで調査し、根拠と修正方針を会話で報告する。
GitHub Issueの作成は、このSkillとは別の明示依頼として扱う。

## 読む資料

このSKILL.mdの実体があるディレクトリから2階層上を`WORKFLOW_ROOT`とする。
リンク経由でも実体を基準に`AGENTS.md`を読み、そこに示す共通規約と対象のローカル指示に従う。
この作業では`rules/coding.md`と`rules/testing.md`も読む。

## 実施

1. 指定範囲と現在のGit状態を読み取りで確認する。
2. 実装と既存仕様を読み、バグ、機能改善、パラメータ名等の改善、規約違反を探す。
3. 原因が同じ指摘はまとめる。単なる好みと客観的な不具合・規約違反を区別する。
4. 影響と確度の高い候補を優先し、通常は重要な五件以内を報告する。無理に件数を埋めない。
5. 報告前に各指摘の根拠を読み直し、確認済みの事実と要検証の内容を区別できているか確認する。
6. ファイルを変更せず、`rules/common.md`の報告項目に従って調査結果を会話で返して停止する。

## 各候補の報告項目

- 一時的な候補ID（例: A01）。GitHubのIssue番号ではない。
- 種別: bug / feature / interface / refactor / style。
- 影響と優先度、確度（確認済み / コード上の根拠あり / 要検証）。
- リポジトリ名、実際のファイルと行番号、問題になる条件。
- なぜ問題か、修正方針の概要、互換性や影響範囲。

## 禁止

- コード、設定、コメント、Git index、ブランチ、Issueを変更しない。
- 検査は`rules/testing.md`の調査用の範囲に従い、元のファイルを書き換えない方法だけを使う。
- 調査結果ファイルやIssue下書きを勝手に保存しない。必要なら会話内に示す。
- GitHub Issueの投稿、登録、ラベル付けをしない。
- 調査後に自動的にkanata-fix / kanata-refactorへ移らない。

## 依頼例

```text
$kanata-audit kanata_coreで改善の余地がありそうな箇所を探してください。修正とIssue登録はしないでください。
```
