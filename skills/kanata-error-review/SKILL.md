# KANATA error review

異常時の動作に集中して、指定された変更を読み取りでレビューする。
確認項目・優先度・報告形式の原本は`rules/error-review.md`とし、このSkillには実行手順を置く。
一般的なコードレビューは`kanata-review`の用途である。

## 読む資料

このSKILL.mdの実体があるディレクトリから2階層上を`WORKFLOW_ROOT`とする。
リンク経由でも実体を基準に`AGENTS.md`を読み、共通規約と対象のローカル指示に従う。
`rules/error-review.md`、`rules/review.md`、`rules/coding.md`、`rules/testing.md`を読む。
必要な規約が取得できなければ、その不足を伝え、レビュー完了とは報告しない。

## 実施

1. 対象リポジトリ、Git状態、比較元・比較先、仕様を特定する。
   未コミット変更はHEADに対するステージ済み・未ステージの差分と対象の新規ファイルを確認する。
   ブランチは指定された比較元との分岐点からの差分を使い、未コミット変更を混ぜない。
   PRはURL、比較元・比較先のコミット、説明と差分を読み取りで確認する。
   Git管理外の検証コードなら変更前後のファイルを特定し、コミット比較ではないことを明示する。
   比較範囲や必要な仕様を調べても判断できない場合だけ質問する。
2. 下の「規約の版情報を記録する」に従い、使う規約と手順の版情報を取得する。
3. 差分と関連する仕様・利用側・設定・テストを読み、`rules/error-review.md`の8観点で確認する。
   検査やCI結果の確認は`rules/testing.md`の調査用の範囲に従う。
4. 候補をコードや仕様と再照合し、原因の重複をまとめる。
   確認できた不具合と、仕様不足による確認事項を分ける。優先度は実際に確認できた影響から選ぶ。
5. 報告前に、対象のコミット・差分・新規ファイルと、規約の版情報を再確認する。
   内容が更新されていれば、どの版を確認した結果かと未確認の変更を伝える。
   古い結果を現在の版の確認結果として扱わない。
6. `rules/error-review.md`の形式で、対象・規約の版情報・確認範囲・指摘・確認事項・検証結果を会話に返して停止する。

## 規約の版情報を記録する

次の読み取り専用スクリプトを実行する。`<WORKFLOW_ROOT>`は上で求めた実体の場所に置き換える。

```bash
python3 <WORKFLOW_ROOT>/skills/kanata-error-review/scripts/collect_rule_context.py
```

JSONには、原本のコミットID、参照元の場所、規約・手順のSHA-256、関連する未コミット変更を記録する。
SHA-256は実際に読み込む内容を区別する値であり、出典の正しさを証明する署名ではない。

- `source_commit`だけでなく、`has_local_changes`と各ファイルの`sha256`も確認する。
  無関係なツール本体などの変更は、この版情報の変更判定に含めない。
- `source_commit`が不明でも、読み取れた本文とハッシュは使える。原本コミット不明と明示し、推測で補わない。
- 対象リポジトリの配布済み規約も参照した場合は、別の参照元として`SOURCE.json`の原本コミットと、実際に読んだファイルのハッシュを記録する。
  配布時のハッシュと一致しなければ、配布後の変更として区別する。異なる版の規約に判断を変える矛盾があれば確認する。
- 他の担当へレビューを引き渡す明示依頼がある場合は、対象の差分・仕様・規約本文にこのJSONも添える。
  メタデータだけを渡し、規約を読めたことにはしない。独立した検証の依頼では、作成者の正解や前回の結論は分ける。
- 報告前に再取得し、`source_commit`、`files`、`git_status`、`collector_sha256`が変わっていないか確認する。
  読み取り失敗のファイルや、取得できない版情報は未確認として残す。

報告の冒頭では原本コミットとローカル変更の有無を短く示し、詳細なファイル一覧とハッシュは必要に応じて折りたたみにまとめる。
レポートやJSONのファイル保存は依頼された場合だけ行い、通常は会話で返す。

## 境界

- コード・規約・設定、Git index・ブランチは変更しない。checkoutによる切替もしない。
- GitHubへの投稿・承認・変更要求・マージ、コミット・push、レビュー後の自動修正は行わない。
- 実機操作や固定回数の再レビュー、複数エージェントの起動を、このSkillだけで許可されたとは扱わない。

## 依頼例

```text
$kanata-error-review kanata_coreの未コミット変更を、異常時の動作に絞ってレビューしてください。
$kanata-error-review kanata_commonの現在のブランチをmainと比較し、処理失敗時の動作を確認してください。
$kanata-error-review このPRをエラー系の観点でレビューしてください：対象のPR URL
```
