# KANATA commit

## 読む資料

このSKILL.mdの実体があるディレクトリから2階層上を`WORKFLOW_ROOT`とする。
リンク経由でも実体を基準に`AGENTS.md`を読み、そこに示す共通規約と対象のローカル指示に従う。
この作業では`rules/git.md`と`rules/testing.md`も読む。

## 実施

1. これはユーザーからの明示的コミット依頼かを確認する。質問・引用・作業予定なら実行しない。
2. 対象Gitルート、ブランチ、HEAD、main、remote、staged/unstaged/untrackedを確認する。
3. コミットする目的と範囲を特定する。「今のもの」は差分を見て判断し、複数の解釈があれば質問する。
4. 関連Issueの扱いと、既存ブランチの再利用・新規作成を`rules/git.md`に従って確認する。
5. 一目的ごとのコミット案を示し、対象だけをステージする。既存の無関係なindexを変えない。
6. staged diffを読み、コミット対象に対して`rules/common.md`の「変更した内容を確認する」を行う。
   検証は`rules/testing.md`に従う。フックが失敗・自動修正したら止め、勝手に再ステージしない。
7. `rules/git.md`の形式と共著表記に従ってメッセージを作り、コミットする。
   任意のメッセージ検査も、同資料の手順を使う。
8. 同資料に従って作成結果と残った差分を確認し、`rules/common.md`の項目で報告する。pushやPR作成はしない。

## 境界

コードを追加修正しない。必要な修正があれば別作業として確認する。
変更の分け方や既存のステージ内容の扱いは、`rules/git.md`に従う。

## 依頼例

```text
$kanata-commit kanata_coreの今の変更を、Issue #102用のブランチを切ってコミットしてください。
$kanata-commit kanata_commonの指定したパッケージの変更だけをコミットしてください。Issueは#88です。
```

番号は例であり、実際の依頼にない番号を補わない。パッケージ名は実物から確認する。
