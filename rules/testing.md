# 変更を確認する方法

変更した内容に合わせて、必要な検査を選びます。
この資料では、CIに任せること、ローカルで試すこと、結果の伝え方を説明します。

## 何を確認するか

| 確認項目 | 確認すること | 使うものの例 |
| --- | --- | --- |
| lint・整形 | 書式やコードの書き方に問題がないか | pre-commit |
| ビルド | コードをコンパイルしたり、パッケージにまとめたりできるか | colcon build |
| 自動テスト | 用意した条件で、期待した結果になるか | unittest、colcon test |
| 動作確認 | 生成したファイルや、起動したものが意図どおりに動くか | 生成物の確認、launchの起動 |

lintはコードの書き方の問題を見つける検査、整形は空白や改行などをそろえる処理です。
pre-commitは、複数の検査や整形をまとめて実行するツールです。

すべての変更で、すべての検査が必要なわけではありません。
例えば、文章だけを変えた場合にROSのビルドまで行う必要はありません。

各Skillでも、この基準に従って必要な検査を選びます。
実機操作の許可範囲は[common.md](common.md)に従います。

## CIとローカルの使い分け

CIは、GitHub Actionsなどで検査を自動実行する仕組みです。
CIで確認できる項目は、その結果を根拠にできます。

ローカルでは、変更した部分の確認や、CIの失敗を再現するために必要な検査を行います。

- AIは、変更に必要なテストを追加・修正します。検査が失敗した場合は、依頼範囲で原因を調べて直します。

- CIの結果は、どのコミットで、何を検査した結果かを確認します。
  スキップされたテストや、実行件数が0件のテストを、動作確認の成功として扱いません。

- コードを変えた後は、関係する検証結果も更新します。
  同じ内容で成功した検査を、追加の変更・失敗・未解決の懸念もないのに繰り返しません。

- CIやテストが用意されていない部分は、未確認の範囲として分けて伝えます。

## 既存の検査設定を使う

対象リポジトリの`.pre-commit-config.yaml`、Gitフック、整形・lint設定、CIの手順を先に読みます。
Gitフックは、コミット時などに自動で処理を実行する仕組みです。
`.clang-format`や`.clang-tidy`などの設定も、使われている場合は確認します。

リポジトリが違えば、設定も違う可能性があります。

- 検査を通すために、無断で設定のバージョンを変えたり、検査を外したり、除外範囲を広げたりしません。
  警告の抑制や設定の変更自体が依頼された場合は、理由を示し、必要な範囲だけ変更します。

- `SKIP`や`--no-verify`で検査を飛ばしません。

- `pre-commit install`は、コミット前に動くGitフックを変更する操作です。依頼なしに実行しません。

## pre-commitを実行する範囲

1. ファイルやパッケージが指定されている場合は、対象ファイルを列挙して`pre-commit run --files ...`を使います。
   リポジトリ全体の検査を依頼された場合は、`pre-commit run --all-files`を使います。

2. 未追跡ファイルは`--all-files`の対象から漏れる場合があるため、必要なら`--files`で指定します。

3. 実行前に、検査設定が指定ファイルだけを扱うか確認します。
   `pass_filenames: false`や独自の実行処理など、全体を処理する設定があるためです。

4. 自動で書き換わった場合は、その内容を読みます。依頼範囲内なら修正後に再検査します。
   範囲外の変更があれば止めて報告し、元からあるユーザーの変更までまとめて戻しません。

各リポジトリのルートで実行し、実行前後の変更を比べてください。

## AIに依頼する作業ごとの違い

| 作業 | 検証するときの範囲 |
| --- | --- |
| refactor：動作を変えない整理 | 指定範囲の整形などを行います。動作変更が必要なら止めて、fix・featとして扱うか確認します。 |
| fix・feat：不具合修正・機能追加 | 変更と直接関係する検査・テストを行います。 |
| commit：既存の変更を記録 | 原則、コミット対象に選んだ変更（ステージ済みの内容）を検査します。新たなコード修正には広げません。 |
| audit：改善候補の調査／review：指定した変更のレビュー | 元のファイルを自動修正する検査は実行しません。変更しない確認方法を使います。 |

コミット時のpre-commitは、ステージしていない変更を一時的によけることがあります。
そのため、実行前にコミット対象と、それ以外の変更を確認します。

別作業の変更がすでにステージされていれば、先に分け方を相談します。
フックが失敗・自動修正した場合は止めて報告し、勝手に再ステージしません。独自フックの動作も確認します。

調査だけの場合は、書き換えをしない検査方法があり、影響がないと確認できたものだけ実行します。
何が起きるか分からないビルドやテストは実行せず、必要なら一時コピーで確認してよいか相談します。

## ビルド・テストと結果の記録

OS・ROS 2・既存の手順を確認し、対象パッケージと必要な依存先に絞って実行します。
バージョンやコマンドを推測で決めず、元の設定や変更を消して検査を通すこともしません。

書式の検査が通っただけで、ビルド・動作・実機の確認まで済んだとは扱いません。

結果には、次の内容を書きます。書式は対象のIssue・PRテンプレートに従います。
「未実施」はまだ検査していない場合、「対象外」は今回の変更にはその検査が不要な場合です。

- 何を確認したかと、実行コマンドまたはCIへのリンク。
- 成功・失敗・未実施・対象外の区別と、その理由。
- 自動テストの実行件数。0件を動作確認済みとしません。
- 未確認の範囲。環境が足りず試せなかった場合と、変更に問題があった場合も分けて説明します。
