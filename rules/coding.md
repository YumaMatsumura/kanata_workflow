# KANATAのコーディング規約

人とAIが、同じ書き方でコードを作成・修正するための規約です。
共通の方針と、言語・用途ごとの規約を分けて記載します。変更する対象に合う章を参照してください。

| 章 | 適用する対象 |
| --- | --- |
| [言語に共通する規約](#言語に共通する規約) | 名前の考え方、外部APIの扱い、読みやすさ |
| [C++の規約](#cの規約) | C++コード、ROS 2のC++実装、GoogleTest、clang-tidy |
| [ROS 2の規約](#ros-2の規約) | パッケージ・ノード名、パラメータ設定、ROSインターフェース、launch、topic |
| [CMakeの規約](#cmakeの規約) | CMakeによるビルド設定と共通マクロ |

C++でROS 2のノードを作る場合は、共通・C++・ROS 2の章を読み、ビルド設定を変更するときはCMakeの章も参照します。
C++固有の規約を、Pythonやシェルスクリプトにそのまま適用しません。
Python・シェルスクリプトの個別規約は、まだ記載していません。
書式やlintは、言語やファイル形式ごとに各リポジトリの設定に従います。
変更する範囲は[変更を必要最小限にする](common.md#変更を必要最小限にする)、
コード整理で動作を変えないことは[既存の変更を守る](common.md#既存の変更を守る)の方針に従います。

## 言語に共通する規約

### 名前の基本方針

名前の意味と省略形は、言語によらず次の方針に従います。
lower_snake_caseは「小文字の単語を`_`でつなぐ書き方」です。
UpperCamelCaseは「各単語の先頭を大文字にしてつなぐ書き方」です。
UPPER_SNAKE_CASEは、大文字の単語を`_`でつなぎます。

| 対象 | 形式 | 例 |
| --- | --- | --- |
| 自作ファイル（ROSインターフェース定義を除く） | lower_snake_case | `joint_controller_component.cpp` |

- `CMakeLists.txt`・`README.md`・`LICENSE`など、慣例やツールで名前が決まっているファイルは、その名前を使います。
- 変数・関数・クラスなどの名前は、原則として単語を省略せず、値・処理・役割の意味が伝わるものにします。
  必要な単位は示し、型の情報や周囲から明らかな説明を詰め込みすぎません。
- 定着した技術用語、規約で定めた略語、狭い範囲で意味が明確な名前は認めます。
- 同じ意味には同じ用語を使い、省略形と正式な単語をむやみに混在させません。
  既存の曖昧な名前を変えるときは、使われ方を確認します。
- 外部APIや生成コードの名前は、[外部で決まっている名前を扱う](#外部で決まっている名前を扱う)の方針に従います。

### 外部で決まっている名前を扱う

外部ライブラリ、生成コード、ROSメッセージなどが決めた名前は、その仕様を優先します。
例えば、C++で基底クラスの関数を上書きするoverrideでは、`setCreateTimerInterface()`などの名前を勝手に変えません。
外部・生成メッセージの定数`Cmd::MODE_MOTION`も、大文字のままで構いません。

他のパッケージから呼ばれる関数など、公開APIの名前を変えるときは、利用している側への影響を調べます。

ROSパラメータ名や`frame_id`も、他の設定やノードから使われるため、名前の変更による影響を確認します。
`kanata_common`などの既存リポジトリ名は、パッケージの命名規則に合わせる目的で改名しません。

### 読みやすさを改善する

後から参加した人も、処理を追える書き方にします。
日本語のコメントには、コードだけでは分かりにくい理由・制約・判断を書きます。
コードをそのまま読み上げるコメントは増やしません。

不要な後続処理へ進まずに関数を抜ける早期return、短い補助関数、意味が分かる定数などを使います。
必要な範囲で処理を簡単にします。
全ノードに新しい基底クラスや設計パターンを強制せず、共通化のために仕組みを複雑にしすぎません。

制御周期内では、読みやすさのために新たなメモリ確保や不要なコピーを増やしません。
実行順序、複数スレッドで使ったときの安全性、計算精度、性能への影響も考えます。

## C++の規約

### 参照先の優先順位

C++の書き方で迷ったときは、次の順に確認します。

1. この資料に書かれたKANATAの規約を優先します。
2. 記載のない項目は、[ROS 2 Jazzyのコードスタイル](https://docs.ros.org/en/jazzy/The-ROS2-Project/Contributing/Code-Style-Language-Versions.html)に従います。
3. さらに判断が必要な設計や安全な書き方は、[C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)を参考にします。

外部の資料は、対象パッケージのC++規格と既存の設定の範囲で参照します。
Autowareの規約は、この資料に取り入れた項目の参考元として扱い、全体をそのまま適用しません。
参考資料と採用範囲は[SOURCES.md](../SOURCES.md)にまとめています。
参考先が更新されても、作業中にKANATAの規約を勝手に変更しません。

### 言語標準

C++の言語標準は、ROS 2 Jazzyに合わせてC++17を基本とします。
新しい規格が必要な場合は、対象環境と依存ライブラリへの影響を確認して変更します。

### C++の名前の付け方

C++のコードには、次の形式を使います。
ファイル名や省略形の基本は、[名前の基本方針](#名前の基本方針)も参照してください。

| 対象 | 形式 | 例 |
| --- | --- | --- |
| C++の名前空間 | `kanata::` + パッケージ由来の名前（lower_snake_case） | `kanata::joint_controller` |
| class・struct・型の別名 | UpperCamelCase | `JointController`, `Parameters` |
| 略語を含む自作の型名 | 略語を1単語として扱うUpperCamelCase | `RosApi` |
| 関数・メソッド | lower_snake_case | `publish_drive_command()` |
| コールバック関数 | lower_snake_case + `_callback` | `high_cmd_callback()` |
| 変数・引数 | lower_snake_case | `target_velocity` |
| privateメンバー | lower_snake_case + `_` | `params_`, `target_velocity_` |
| Publisher | `pub_` + lower_snake_case（privateメンバーは末尾に`_`） | `pub_high_cmd_` |
| Subscriber | `sub_` + lower_snake_case（privateメンバーは末尾に`_`） | `sub_low_state_` |
| Service server | `srv_` + lower_snake_case（privateメンバーは末尾に`_`） | `srv_reset_` |
| Service client | `cli_` + lower_snake_case（privateメンバーは末尾に`_`） | `cli_reset_` |
| Action server | `act_srv_` + lower_snake_case（privateメンバーは末尾に`_`） | `act_srv_follow_trajectory_` |
| Action client | `act_cli_` + lower_snake_case（privateメンバーは末尾に`_`） | `act_cli_follow_trajectory_` |
| structの公開データメンバー | lower_snake_case | `control_period` |
| C++で定義する定数・constexpr | lower_snake_case | `num_legs`, `four_pi` |
| enum classの型名 | UpperCamelCase | `DriveMode` |
| 自作の列挙子 | UpperCamelCase | `DriveMode::Free` |
| GoogleTestのテストスイート名・テスト名 | UpperCamelCase（アンダースコアを使わない） | `JointLimitTest`, `RejectsOutOfRangePosition` |
| 自作マクロ・ヘッダーの重複読み込みを防ぐinclude guard | UPPER_SNAKE_CASE | `JOINT_CONTROLLER_COMPONENT_HPP_` |

- 表の「パッケージ由来の名前」は、パッケージ名から先頭の`kanata_`を除いた部分を基本にします。
- 既存の書き方も確認し、Publisher・Subscriberを好みだけで`xxx_pub_`・`xxx_sub_`へ一括置換しません。
- マクロ・include guardは、既存の整形設定・guard規約を優先します。

### C++パッケージのディレクトリ構造

コンポーネントを含むC++パッケージでは、ヘッダーの用途に応じて配置を選びます。
ファイル名は[名前の基本方針](#名前の基本方針)、クラスや名前空間の規則は[C++の名前の付け方](#cの名前の付け方)に従います。

ここでの「公開」は、他のパッケージから`#include`して使えるようにすることです。

| ヘッダーの用途 | 配置 |
| --- | --- |
| 他のパッケージから使う公開ヘッダー | `include/<パッケージ名>/` |
| パッケージの内部だけで使うヘッダー | 対応する`.cpp`と同じ`src/`内 |
| テストだけで使うヘッダー | `test/`内 |

`include/`には公開するヘッダーだけを置き、内部用・テスト用のヘッダーは公開用としてインストールしません。
コンポーネントとして読み込むだけなら、ヘッダーを公開する必要はありません。

#### 公開ヘッダーがない場合

`include/`を作らず、内部用のヘッダーと実装を`src/`に置きます。

```text
kanata_joint_controller/
├── package.xml
├── CMakeLists.txt
├── README.md
└── src/
    ├── joint_controller_component.hpp
    └── joint_controller_component.cpp
```

#### 公開ヘッダーがある場合

他のパッケージからコンポーネントのクラスを直接使う場合の例です。

```text
kanata_joint_controller/
├── package.xml
├── CMakeLists.txt
├── README.md
├── include/
│   └── kanata_joint_controller/
│       └── joint_controller_component.hpp  # クラスなどの宣言
├── src/
│   └── joint_controller_component.cpp      # 処理の実装
├── launch/
│   └── joint_controller.launch.xml         # 起動設定
├── config/
│   └── joint_controller.params.yaml        # パラメータ設定
└── test/
    └── test_joint_controller.cpp           # 自動テスト
```

#### どちらの構成にも共通する補足

`launch/`・`config/`・`test/`は、置くファイルが必要になったときに追加します。
空のフォルダをそろえる必要はありません。ライブラリだけのパッケージなどには、同じ構成を一律に求めません。

単体で起動できる実行ファイルも用意する場合は、CMakeの`rclcpp_components_register_node()`で
`EXECUTABLE joint_controller_node`を指定すると、`main()`を含むソースと実行ファイルがビルド先に生成されます。
単純な起動処理だけなら、ソースとして管理する`joint_controller_node.cpp`を別途用意する必要はありません。
独自の起動処理が必要な場合は、`src/`に`main()`用のファイルを追加できます。

### ヘッダー・型・初期化

- 自パッケージのヘッダーは`"..."`、他パッケージ・ROSメッセージ・標準ライブラリは`<...>`を基本にします。
- includeの順番や空白は、既存の`.clang-format`とpre-commitの設定に従います。
  原則は、そのソースに対応するヘッダー、自パッケージ、他パッケージ、メッセージ、外部・標準ライブラリの順です。
- `#include`行の間に`#define`を挟みません。ヘッダーの動作を切り替えるマクロが必要なら、include群より前に置きます。
  特定の位置で定義する必要がある場合は、その理由をコメントに書きます。
- 直接使う型に必要なヘッダーを読み込みます。別のヘッダーが偶然読み込んでいることだけに頼りません。
- ビット数が決まった整数を必要とする仕様には、`std::int64_t`・`std::uint8_t`などを使います。
  型を変えると、表せる範囲や符号、桁あふれの動作も変わることがあります。単なる書式の修正として扱いません。
- ROSの整数パラメータは、APIが扱う型に合わせます。より狭い型へ変換する場合は、値が収まるか確認します。
- 変数の初期化漏れや、参照先のデータが使う前に破棄されないか、誰がデータを管理するかに注意します。
  Eigenには、式を書いた時点では計算せず、後で評価する仕組みがあります。Eigenの式を安易に`auto`で保持しません。

### ROS 2のノードとコンポーネントを作る

通常の`rclcpp::Node`を使うコンポーネントでは、コンストラクタに`explicit`を付け、
`const rclcpp::NodeOptions &`を引数で受け取ります。受け取った設定は、基底クラスの`rclcpp::Node`にも渡します。
起動時のパラメータなどを、ノードへ反映するためです。

ノードクラスでの宣言例です。

```cpp
explicit JointController(const rclcpp::NodeOptions & options);
```

名前空間の閉じ括弧には、名前空間名をコメントに書きます。
コンポーネントは`<rclcpp_components/register_node_macro.hpp>`を読み込み、名前空間を閉じた後、
ソースファイルの末尾で登録します。登録には、名前空間を含む完全なクラス名を使います。

ソースファイル末尾の例です。

```cpp
namespace kanata::joint_controller
{
// ノードの実装
}  // namespace kanata::joint_controller

#include <rclcpp_components/register_node_macro.hpp>
RCLCPP_COMPONENTS_REGISTER_NODE(kanata::joint_controller::JointController)
```

### C++でROS 2のパラメータをまとめる

パラメータが多い場合は、`parameters.hpp`という別のヘッダーに構造体をまとめます。
構造体の名前は`Parameters`、または用途に合うUpperCamelCaseとし、ノードでは`params_`などのメンバーに保持します。
複数の設定値をまとめて保持し、値を確認しやすくするためです。

設定ファイルや既定値、実行中の変更の基本方針は、[ROS 2のパラメータをまとめる](#ros-2のパラメータをまとめる)に従います。

#### 値を確認する

パラメータを構造体でまとめる場合は、できる限り`void validate() const`を設けます。
仕様に基づいて、値の範囲、無限大やNaN（数値ではないことを表す値）でないこと、他のパラメータとの組み合わせなどを確認します。
この検査で不正な値を見つけたら、`std::invalid_argument`などの例外を出し、パラメータ名と満たすべき条件をメッセージに書きます。
起動時は、この例外で設定の不正を知らせ、初期化を中断します。
仕様にない制限を、推測で追加しません。

#### ノードで宣言して使う

`Parameters`構造体を使うノードでは、`Parameters declare_and_validate_parameters()`を設けます。
構造体名を変えた場合は、戻り値の型も合わせます。

1. ローカル変数`params`を用意します。
2. `this->declare_parameter<>()`が返す値を、`params`に代入します。
   宣言した直後に、`this->get_parameter()`で同じ値を読み直しません。
3. `params.validate()`で値を確認してから、`params`を返します。
4. ノードの初期化時に呼び出し、確認した値を使って他の初期化を進めます。

次はノードクラス側の例です。パラメータ名・型・既定値は説明用です。

```cpp
Parameters declare_and_validate_parameters()
{
  Parameters params;
  params.control_period = this->declare_parameter<double>("control_period", 0.01);
  params.validate();
  return params;
}
```

ノードの初期化時には、`params_ = declare_and_validate_parameters();`などで呼び出します。

宣言済みの値の取得や実行中の更新に必要な場合は、既存の動作を保って読み直します。

#### 実行中の変更で例外を扱う

更新候補の検査も、[値を確認する](#値を確認する)の方針に従います。
`validate()`の例外を利用する場合は、変更前に値を検査するコールバック内で受け止め、
変更結果（`rcl_interfaces::msg::SetParametersResult`）に拒否と理由を設定します。

### C++のテストコードの書き方

テストでは、仕様で決めた動作を確認し、失敗したときに何が違ったか分かるようにします。

1. **既存の仕組みにテストを登録する。** C++の単体テストはGoogleTestを基本とし、`BUILD_TESTING`内でamentのテスト機能に登録します。
   テスト用の依存は、`package.xml`の`test_depend`に記載します。
2. **確認する条件と期待する動作が分かる名前にする。** `TEST`・`TEST_F`のテストスイート名とテスト名は、[C++の名前の付け方](#cの名前の付け方)のGoogleTest用の行に従います。
3. **検証マクロを使い分ける。** 通常の確認には`EXPECT_*`を使い、失敗すると後続の確認ができない前提には`ASSERT_*`を使います。
   `ASSERT_*`は、失敗した場合に現在の関数の後続処理を打ち切ります。例えば配列の要素数を確認してから、要素を参照します。
   浮動小数点の計算結果は、仕様に応じた許容誤差で比較します。
4. **仕様に基づいて確認する内容を選ぶ。** 正常値・境界値・不正値から必要な条件を選び、不具合修正では再発を検出できるテストを追加します。
   実装と同じ計算をコピーして期待値を作るだけのテストは避けます。
5. **テストを独立して実行できるようにする。** 実行順序や他のテストが残した状態によって結果が変わらないように、必要な初期化と後片付けを行います。
   単体テストは、できる限り実機や外部サービスなしで実行できるようにします。
6. **ROS通信を使うテストを分離する。** `ament_cmake_ros`の隔離機能などで、並列実行する別のテストと通信が混ざらないようにします。
   待機にはタイムアウトを設け、終了時にノードやプロセスを片付けます。計算関数だけのテストでは、不要なROSノードを起動しません。

ファイルの配置は[ディレクトリ構造](#cパッケージのディレクトリ構造)、
変更に応じた検査の選び方・実行・結果報告は[検証の規約](testing.md)に従います。

### clang-tidyを活用する

C++では、clang-tidyによる静的解析（コードを実行せずに問題を調べる検査）を活用します。
書き方の問題や、バグにつながる記述を見つけるための補助として使います。

導入済みのリポジトリでは、検査項目と実行方法は`.clang-tidy`やCIなどの既存の設定に従います。
ツールの導入や検査設定の追加・変更は、規約の整理とは分けて行います。

clang-tidyだけで、すべての規約や実行時の動作を確認できるわけではありません。
[検証の規約](testing.md)に従い、変更内容に応じてビルド・テスト・レビューと組み合わせます。

### C++のROSノードでログを出す

ROSノードのログには、`printf`や`std::cout`ではなく、`RCLCPP_INFO`などの`RCLCPP_*`マクロを使います。
出力先や表示する重要度を、ROSの設定でまとめて扱うためです。
ログの重要度は、[ROSのログの重要度](#rosのログの重要度)で選びます。

同じ待機メッセージや警告が繰り返され、重要なログが埋もれる場合は、
`RCLCPP_*_THROTTLE`などで出力間隔を制限します。毎回の記録が必要な出来事や、DEBUGのログは状況に応じて扱います。

## ROS 2の規約

### ROSの名前の付け方

パッケージやROS上の名前は、実装に使う言語によらず次の形式を使います。
launchの`name`はROS上で識別するノード名、XMLの`exec`（Pythonの`executable`）は起動するプログラムのファイル名を指定します。

| 対象 | 形式 | 例 |
| --- | --- | --- |
| パッケージ | `kanata_` + lower_snake_case（末尾に`_node`を付けない） | `kanata_joint_controller` |
| ROSノード名 | lower_snake_case（末尾に`_node`を付けない） | `joint_controller` |
| ノードを起動する実行ファイル名 | lower_snake_case + `_node` | `joint_controller_node` |
| ROSインターフェースのファイル | UpperCamelCase + `.msg`・`.srv`・`.action` | `JointCommand.msg`, `ResetController.srv`, `FollowTrajectory.action` |
| ROSインターフェースのフィールド | lower_snake_case | `target_position` |
| ROSインターフェースの定数 | UPPER_SNAKE_CASE | `MODE_STOP` |

### ROS 2のパラメータをまとめる

#### 設定ファイルとコードを合わせる

パラメータを追加・削除・変更したら、関係するYAMLと説明も確認し、名前・型・既定値などの変更を反映します。
既定値は、利用者が値を指定しなかった場合に使う値です。
共通の既定値と、実機用に上書きする設定値を区別して管理します。
用途・単位・仕様で決まった範囲は、YAMLのコメントなど、設定する人が確認できる場所に記述します。

複数ノードの設定は1つのYAMLにまとめても構いません。
その場合は、ノードを指定するキーと`ros__parameters`で適用先を区別し、意図しないノードに設定が適用されないようにします。
ファイルの差し替え方は、[launchの書き方](#launchの書き方)に従います。

#### 既定値と必須指定を分ける

共通で使える値には既定値を設けます。
実機固有で推測できない値は指定必須とし、未指定なら起動時に検出します。

#### 実行中の変更を扱う

各パラメータが起動時だけ使う設定か、実行中の変更にも対応する設定かを明記します。
変更に対応する場合は、仕様に基づいて更新候補の値を検査します。
不正なら変更を拒否し、理由を返します。
検証中はノードが保持する設定値を書き換えず、すべての検査を通って変更が受理された後で、実際の処理へ反映します。
変更に対応しないパラメータは、更新を受け付けないようにします。

パラメータ名・型・既定値・単位、宣言の順番や更新時の動作は、互換性に関わるため、変更の影響を確認します。

C++での構造体や宣言・検証の実装は、[C++でROS 2のパラメータをまとめる](#cでros-2のパラメータをまとめる)を参照してください。

### ROSインターフェースの書き方

ノード間でやり取りするデータや要求・応答を定義する`.msg`・`.srv`・`.action`では、次の方針を使います。

1. **名前の付け方を統一する。** ファイル・フィールド・定数の形式は、[ROSの名前の付け方](#rosの名前の付け方)のROSインターフェース用の行に従います。
2. **定義ファイルに値の意味を書く。** 冒頭に用途を書き、各フィールドには意味と、物理量なら単位をコメントで記述します。
   必要に応じて有効範囲、座標系、時刻が表すタイミング（取得時・送信時など）も説明します。
3. **単位を統一する。** 距離はm、角度はrad、時間はsなど、ROSの標準単位を基本にします。
   標準単位ではフィールド名に単位を付けず、例外では`_deg`・`_ms`などを末尾に付けます。単位の基本は[REP-103](https://github.com/ros-infrastructure/rep/blob/master/rep-0103.rst)を参照します。
4. **未取得・無効な値の扱いを決める。** 値を使えない場合の表し方と、受信側がどう判断するかを定義します。
   既定値が、そのまま有効な値とは限りません。関節角度の`0`など、正常な値にもなる数値を説明なしに「未取得」として使いません。
   コメントに`optional`と書くだけでは、フィールドを省略できる仕組みにはなりません。有効フラグなど、必要な表現方法を仕様として決めます。
5. **状態を意味の分かる定数で表す。** 動作モードなど、通常の状態分類には異なる値を割り当てます。
   定義されていない値を受信した場合の扱いも決めます。
6. **配列の長さと対応関係を決める。** 要素数が固定なら固定長、上限が決まっていれば上限付き、それ以外は上限なしの可変長を検討します。
   脚・関節などの並び順や、複数の配列で同じ要素をどう対応させるかを、利用する側が判断できるようにします。

### launchの書き方

launchは、起動するノードと設定の関係を読み取れるように、次の方針で書きます。
ノード名と実行ファイル名の区別は、[ROSの名前の付け方](#rosの名前の付け方)を参照してください。

1. **基本はXMLにする。** `.launch.xml`で実装します。
   XMLでは表現しにくい処理が必要な場合だけPythonを使い、その理由を残します。
2. **全体の入口と機能別の起動設定を分ける。** `bringup.launch.xml`などの入口から、機能別のlaunchを`include`します。
   まとめて起動・再利用したい単位で分け、階層やファイルを必要以上に増やしません。
3. **個別パッケージの起動設定と、KANATA全体の設定を分ける。** 個別パッケージには、必要に応じて単独で試すためのlaunchと設定を用意します。
   特定のPCやロボット構成に合わせたノードの組み合わせは、`kanata_operation_launch`などの統合用パッケージで扱います。
4. **外から変更する設定はlaunch引数で受け取る。** パラメータファイルのパスなど、利用時に差し替えるものを引数にし、用途が分かる説明を付けます。
   共通で使える既定値があれば用意し、上位のlaunchから受け取った値は必要な呼び出し先へ渡します。
5. **必要な機能を選んで起動できるようにする。** 一部だけを試す必要がある機能には、`launch_rviz`など、起動するかどうかを選ぶ引数を用意します。
   すべてのノードに個別の切り替えを設ける必要はありません。

パラメータ設定の管理は、[ROS 2のパラメータをまとめる](#ros-2のパラメータをまとめる)を参照してください。
C++パッケージ内のlaunch・configの配置は、[ディレクトリ構造](#cパッケージのディレクトリ構造)を参照してください。
topicの接続と名前空間は、[topic名とROSの名前空間](#topic名とrosの名前空間)に従います。

### topic名とROSの名前空間

自作ノードの既定のtopic名と、システム内で実際に接続するtopic名を分けて管理します。
ROSの名前空間は、`/kanata/control`のように、ノードやtopicの名前を階層で整理するためのものです。

#### コード内のtopic名

自作ノードでは、次の形式を基本にします。
`~`は、ノードのROS名前空間とノード名を合わせた名前に展開されます。

| 用途 | 形式 | 例 |
| --- | --- | --- |
| 購読する入力 | `~/input/...` | `~/input/path` |
| 配信する出力 | `~/output/...` | `~/output/path` |
| 可視化・調査用の出力 | `~/debug/...` | `~/debug/processing_time` |

ソースに`/kanata/...`などのシステム固有の絶対名を固定しません。
外部パッケージや標準で決まっているtopic名は、その仕様を尊重し、必要な接続をlaunchで設定します。

#### launchで名前空間と接続先を決める

launchで、ロボット名（`kanata`）と機能ごとのROS名前空間を各ノードへ適用します。
機能区分は`operation`・`localization`・`control`など、役割のまとまりを表します。
コンポーネントのクラス名やコンテナ名と一致させる必要はなく、1つの機能の名前空間に複数のコンポーネントを配置できます。
C++の名前空間とも別のものです。

ノード間の接続は、統合用launchの`remap`で、配信側と購読側を同じtopic名に対応させます。
接続先はロボット名・機能・データの意味で整理し、具体的な分類や階層は構成に合わせて決めます。
次は接続先の説明用の例です。

| ノード | コード内の指定 | remap後の接続先 |
| --- | --- | --- |
| `path_planner` | `~/output/path` | `/kanata/planning/path` |
| `trajectory_follower` | `~/input/path` | `/kanata/planning/path` |

#### 起動後の接続を確認する

remapは名前の置き換えであり、元のtopic名を別名として残すものではありません。
`ros2 topic list`には実際に使われる名前が表示されるため、配信元・購読先のノード名は
`ros2 topic info <topic名> --verbose`や`ros2 node info <ノード名>`で確認します。
デバッグ用の出力は、接続先を変える必要がなければ`~/debug/...`のまま使います。

### ROSのログの重要度

ROSノードのログの重要度は、次の基準で選びます。

| 重要度 | 使う場面 |
| --- | --- |
| DEBUG | 開発者向けの詳しい確認情報 |
| INFO | 起動や状態変更など、通常の動作で知らせたい出来事 |
| WARN | 正常な動作を継続できるものの、注意が必要な状態 |
| ERROR | ノードが正常な動作を継続できない状態 |
| FATAL | システムが正常な動作を継続できず、停止が必要な状態 |

## CMakeの規約

### ターゲットごとに設定する

CMakeは、ライブラリや実行ファイルなどの「ターゲット」ごとに設定する書き方を基本にします。
一般にモダンCMakeと呼ばれる書き方です。

| 設定するもの | 使うコマンド |
| --- | --- |
| ヘッダーの検索先 | `target_include_directories()` |
| リンクするライブラリ | `target_link_libraries()` |
| コンパイル時の定義 | `target_compile_definitions()` |
| コンパイラのオプション | `target_compile_options()` |
| C++の言語標準など | `target_compile_features()` |

`PUBLIC`・`PRIVATE`・`INTERFACE`は、設定を適用する範囲で選びます。
ここでの「利用側」は、そのライブラリなどをリンクして使うターゲットです。

| 指定 | 設定を適用する範囲 |
| --- | --- |
| `PRIVATE` | ターゲット自身だけ |
| `PUBLIC` | ターゲット自身と利用側 |
| `INTERFACE` | 利用側だけ |

公開ヘッダーを使うために必要な設定も、この範囲を確認して指定します。
依存先がヘッダーの場所やリンク情報を設定したターゲット（imported target）を提供していれば、それを優先し、
ヘッダーやライブラリの場所を手動で指定する箇所を減らします。

`include_directories()`・`link_directories()`・`add_definitions()`や`CMAKE_CXX_FLAGS`の直接変更は、
ディレクトリ全体に影響します。必要な理由がない限り追加しません。
ただし、`kanata_cmake`などの共通マクロが用意する既定設定は、実際の処理と使い方を確認します。
モダンCMakeへ書き方を揃えるためだけに、共通マクロを作り直しません。

#### ROS 2とKANATAの共通マクロを使う

利用中のROS 2とパッケージ構成で対応できる場合は、`ament_cmake_auto`と`ament_auto_*`を優先します。
依存関係の読み込みや、ライブラリ・実行ファイルの追加をまとめて扱うための仕組みです。

| 処理 | 使うマクロ |
| --- | --- |
| 依存パッケージを探す | `ament_auto_find_build_dependencies()` |
| ライブラリを追加する | `ament_auto_add_library()` |
| 実行ファイルを追加する | `ament_auto_add_executable()` |
| KANATA共通の初期設定 | `kanata_package()` |
| KANATAパッケージの最後の処理 | `kanata_auto_package()` |

`kanata_cmake`を使うパッケージでは、初期設定に`kanata_package()`、最後に`kanata_auto_package()`を使います。
`kanata_auto_package()`は`ament_auto_package()`を呼び、`USE_SCOPED_HEADER_INSTALL_DIR`を共通で指定します。
ヘッダーをパッケージ名で分けた場所へインストールするための設定です。
`kanata_cmake`自身など、共通の仕組みを最初に作るパッケージは、通常のamentマクロを使います。
自分自身を依存パッケージとして使う構成を避けるためです。

`package.xml`には、実際に使う依存パッケージを書きます。
`ament_cmake_auto`を使う場合は、ビルド用ツールの依存（buildtool）としても宣言します。
自動処理で扱えない外部依存、コード生成、個別のインストールや利用側への設定公開（export）は、別途記述します。
自動処理が適さない場合は理由を説明し、通常の`ament_cmake`などで必要な処理を書きます。

ターゲット名、依存関係、公開する設定、インストール先、exportの動作を変更するときは、利用側への影響を確認します。
規約に合わせるためだけにCMake・ROS 2のバージョンや言語標準を引き上げず、既存の環境で使える機能を確認します。
