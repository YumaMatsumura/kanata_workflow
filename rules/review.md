# 変更をレビューする

変更が目的を満たし、新しい問題を持ち込んでいないか確認するための、人とAIに共通する基準です。
指定された未コミットの変更、ブランチやコミットの差分、PRに使います。
例えば、PRで追加・変更した処理が適切かを確認するのがレビューです。
変更箇所に限らず改善候補を広く探す調査（audit）とは、対象を分けて扱います。

## 確認する範囲

変更前と変更後を比べ、変更した箇所と、影響を受ける利用側・設定・テストを確認します。
差分だけで判断できない場合は、周辺コードや依存先の仕様も調べます。
もともとある問題は、今回の変更で発生・悪化した問題と区別します。

## 変更内容に合わせて観点を選ぶ

すべての変更に同じ検査を求めず、関係する観点を確認します。

| 観点 | 確認すること |
| --- | --- |
| 目的と範囲 | 依頼された目的・完了条件を満たし、無関係な変更が混ざっていないか |
| 動作と異常時の扱い | 正常時に加え、上限・下限付近の値や不正な入力、通信の切断、状態の切り替えなど、関係する条件で仕様に沿って動くか |
| 互換性とセキュリティ | 利用側が依存する名前や動作を壊していないか。外部入力・権限・秘密情報の扱いに、変更による問題がないか |
| 規約と可読性 | 適用する規約を守り、処理や変更理由を追えるか。不要な複雑さを増やしていないか |
| 検証 | 変更に必要な条件をテストで確認でき、検証結果が対象の変更に対応しているか |

変更範囲は[common.md](common.md#変更を必要最小限にする)、コードの規約は[coding.md](coding.md)、
検証方法とCI結果の扱いは[testing.md](testing.md)に従います。
書式などCIで確認する項目の指摘を重複させず、CIが何を確認したかも区別します。

## 指摘の根拠を確かめる

- 候補を見つけたら、該当コードや仕様を読み直し、問題になる条件と影響を確かめます。
- 規約違反を指摘するときは、その規約が対象のファイルや変更に適用されるか確認します。
- 特定の入力や状態で起きる問題も対象にします。仕様が不明な場合は、推測で不具合と断定せず、確認が必要な点を示します。
- 同じ原因の指摘はまとめます。個人の好みや任意の改善案は、修正が必要な問題と分けます。

## 結果を伝える

最初に対象リポジトリと、どの変更前・変更後を比べたかを示します。
ブランチ名やコミットID、まだコミットしていない変更を含めたかも記載します。
指摘は優先度の高いものから、次の内容を簡潔に説明します。

- 問題の内容、優先度とその理由。
- 該当ファイルと行番号、問題が起きる条件、利用側への影響。
- 根拠となるコード・仕様・規約と、修正方針の概要。

確認したことと未確認のことを分け、指摘がない場合も確認範囲を伝えます。
「問題が見つからなかった」ことだけで、動作や安全性を保証したとは扱いません。
文章と図の使い方は[communication.md](communication.md)に従います。
