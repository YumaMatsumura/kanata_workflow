# Gitで変更を管理する

この資料では、作業ブランチの作り方と、変更をコミットするときのルールを説明します。
人とAIは同じ規約を使います。AIが操作するときの許可範囲も、ここで決めます。

コミットは、変更を手元のGit履歴に記録する操作です。
pushは、そのコミットをGitHubなどの共有先（リモート）へ送る操作です。
Issueは課題を記録するもの、PR（Pull Request）は変更を取り込んでもらうための依頼です。

## AIに任せる範囲

AIは、コミットを明確に依頼された場合にだけコミットします。
コード整理・不具合修正・機能追加などの作業依頼だけでは、コミットまで許可されたとは扱いません。

ブランチの作成・切替・ステージ操作は、その操作を依頼された場合か、許可されたコミット作業に必要な場合に行います。

push、PRの作成・マージ、Issueの作成・更新・クローズは、それぞれ明示的な依頼が必要です。
コミットの依頼だけで、これらも許可されたとは扱いません。

コミット用のSkillは、既存の変更を整理して記録するためのものです。コードを追加で修正する作業には広げません。

## 作業ブランチを使う

ブランチは、作業ごとに変更の履歴を分けて管理する仕組みです。
`main`を変更の取り込み先とし、作業ごとに短期間使うブランチを作ります。
作業ブランチから`main`へのPRを作成し、確認後に取り込みます。

- 新しいブランチは、対象リポジトリの`main`を確認してから作ります。

- 人が作る場合は、`feat/説明`、`fix/説明`、`docs/説明`、`refactor/説明`、`chore/説明`などを使います。
  説明は英語の小文字で書き、単語を`-`でつなぎます。例：`feat/add-joint-controller`。

- Codexが作る場合は、明示指定がなければ`codex/説明`を使います。
  ユーザー指定の名前や、同じ作業のためにあるブランチを優先します。
  新規作成が許可され、名前の指定がない場合は、この命名規則に沿って作業内容から名前を決めます。

- 同じIssue・目的のブランチは再利用できます。

- Issueが指定されていれば、対象リポジトリと番号を確認し、コミット本文とPRに記載します。
  番号をブランチ名に入れる必要はありません。Issueがなければ、番号を作らず進めます。
  Issueの登録・更新には、その操作の依頼が必要です。

Codexが新しいブランチを作る例です。対象や開始位置を確認してから使ってください。

```bash
git -C <対象リポジトリ> switch -c codex/add-joint-controller main
```

現在のコミットから分岐しただけでは、`main`から分岐したとは限りません。
`main`がない、ブランチから外れた状態（detached HEAD）、別作業のブランチ上、
リモートとの差が大きい場合は、状態と必要な操作を説明して確認します。

別作業の変更を勝手に取り込んだり、stashやresetで移動・消去したりしません。

取得先のURLと既存のブランチ名は、実物を確認します。
リモートから履歴を取得する`fetch`は、ネットワークの権限に従って行います。
取得していなければ、リモートの最新状態は未確認と報告します。

pull・merge・rebaseで勝手に同期しません。

## コミットに含める変更を選ぶ

コミットする前に、含める変更を選びます。この操作を「ステージ」と呼びます。

- 1コミットは1つの目的にします。その修正に必要なコード・設定・テストは一緒に含めて構いません。

- 無関係な機能追加、不具合修正、書式変更などを混ぜません。

- 指定されたパッケージやファイルだけを扱います。それだけでは修正が成り立たない場合は、必要な追加範囲を説明します。

- 対象の変更、分け方、使うブランチを短く伝えてからステージします。すでにあるコミット依頼を再確認する必要はありません。

- `git add .`、`git add -A`、`git commit -a`で、変更を一括して取り込みません。

- 同じファイルに別目的の変更が混ざっている場合は、変更箇所ごとに分けます。
  安全に分けられない場合や、範囲の追加が必要な場合は確認します。

- 別作業の変更がすでにステージされていた場合は、混ぜたり選択を解除したりせず、分け方を相談します。

- コミット前に、ステージされた変更を読み、意図した内容だけが含まれているか確認します。

## メッセージの書き方

次の形式を使います。説明は、英語の小文字の動詞で始めます。

```text
type(scope): english description
```

`type`は変更の種類です。`feat`は機能追加、`fix`は不具合修正、`docs`は文書変更に使います。
使用する種類は`feat`, `fix`, `refactor`, `test`, `build`, `ci`, `chore`, `docs`, `perf`, `revert`です。

`scope`には、対象のKANATAパッケージ名やコンポーネント名を書きます。
パッケージに属さない変更では、規約なら`rules`、CI設定なら`ci`など、対象の資料や仕組みの名前を使います。

例えば、規約の説明を直す変更は`docs(rules): clarify branch naming rules`と書けます。
単に「update」などとせず、何を変えるのかが分かる説明にします。

この形式は、KANATAで通常の作業コミットに採用しているものです。
GitHubなどが作るマージコミットには強制しません。

以下は、関連IssueとCodexの共著表記を含めた例です。
`owner`とIssue番号は説明用なので、そのまま使わないでください。

```text
refactor(kanata_joint_controller): clarify command conversion logic

Refs: owner/kanata_core#102

Co-authored-by: Codex <noreply@openai.com>
```

## AIが関与した場合の表記

AIが関与した変更には、ユーザーから別の指定がなければ`Co-authored-by`を付けます。
コミット末尾に、作成に関わったAIを記録するための行です。人だけで作成した変更には付けません。
Codexの場合は、上の例にある次の行を1回だけ付けます。

```text
Co-authored-by: Codex <noreply@openai.com>
```

- `Assisted-by`との使い分けは行いません。

- Codex以外のAIでは、表記とメールアドレスを確認して使います。推測で作りません。

- AIはコミット作業のために`user.name`・`user.email`を変更しません。
  変更の作成者（author）・コミットを記録する人（committer）の設定もAI名に上書きしません。

- `Signed-off-by`は別の表記です。自動では追加せず、必須のリポジトリではユーザーの設定と承認を確認します。

- AIが関与していないとユーザーが説明した変更など、記録と実際の関与が食い違う場合は確認します。

互換性を壊す変更が明示的に許可された場合だけ、件名の`!`と本文の説明を使います。
単なるコード整理の依頼を、互換性を壊す変更の許可として扱いません。

## メッセージを検査する

[check_commit_message.py](../scripts/check_commit_message.py)で、件名などの形式を確認できます。
次のコマンドは`kanata_workflow`のルートで実行します。`/path/to/message.txt`は、用意したメッセージファイルに置き換えます。

```bash
# 人だけで作成したコミット：件名と本文の区切りを確認する
python3 scripts/check_commit_message.py --file /path/to/message.txt

# Codexが関与したコミット：共著表記も確認する
python3 scripts/check_commit_message.py --file /path/to/message.txt --require-codex
```

この検査はメッセージを書き換えず、Gitフックも導入しません。
変更を1つの目的にまとめられているか、英語が自然か、Issueや共著表記が正しいかは、内容を読んで判断します。

## コミット前後の確認

コミット前に[testing.md](testing.md)に従って検証し、`--no-verify`などで検査を回避しません。
コミット後は、メッセージ・共著表記・含まれた変更と、まだ残っている変更を確認します。
不備があっても、既存のコミットを修正する`amend`などで無断で履歴を書き換えず、報告します。

作業結果は[common.md](common.md)の終了報告に従い、関連Issueがあれば併記します。
