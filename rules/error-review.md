# エラー時の動作をレビューする

エラー系専用レビューは、不正な入力や通信の途絶、処理の失敗が起きたときに、変更後のコードがどう動くかを確認します。
人とAIが使う確認項目と、結果の報告形式をまとめた資料です。

現時点では設計資料です。このファイルを置くだけで、専用レビューが自動実行されるわけではありません。

## 既存のレビューとの関係

レビュー全体の範囲、指摘の根拠、既存の問題との区別は、[review.md](review.md)に従います。
専用レビューでは、その中の「動作と異常時の扱い」に集中します。
通常のコードレビューでも異常時の問題を指摘できますが、専用レビューでは以下の確認項目を意識して調べます。

コードや設定の書き方は[coding.md](coding.md)、検証結果の扱いは[testing.md](testing.md)、
説明の書き方は[communication.md](communication.md)を参照します。
コード修正・実機操作・GitHubへの投稿の許可範囲を、この資料で広げることはありません。

## 確認する対象を選ぶ

最初に、対象の変更に関係する処理、設定、仕様、利用側、テストを確認します。
異常が「起きる」「検出される」「状態や出力へ反映される」「復旧する」までを、関係する範囲で追います。

- ROSノードだけでなく、CMake・launch・スクリプトの失敗時の動作も対象にします。
- 変更に関係する項目だけを選びます。通信しない処理に通信断の対策を求めるなど、全項目を一律に要求しません。
- 停止方法、許容する入力、待ち時間、復旧条件は、確認できた仕様や利用側の契約を根拠にします。
  AIが数値や動作を勝手に決めません。常にゼロ指令を出すことや、常にプロセスを終了することを正解としません。
- 仕様が不足する点は、不具合と断定せず「判断に必要な情報」として報告します。
  コードから確かめられる事実と、仕様がないため判断できないことを分けます。

## 確認項目

| 観点 | 確認すること | 問題になる例 |
| --- | --- | --- |
| 不正な入力・設定 | 値や長さなどを、使う前に必要な範囲で検査しているか | 空の配列を参照する、範囲外の値やNaNを計算へ流す |
| 起動・初期化の失敗 | 必要な依存先や設定が使えないとき、失敗を検出して仕様に沿って中断・待機するか | 設定ファイルの読み込みに失敗しても、起動成功として処理を続ける |
| 通信の途絶・古いデータ | 入力が来ない場合や期限切れの場合に、状態と出力が仕様どおりになるか | 指令の受信が止まっても、前回の指令を有効なまま使う |
| 待機・再試行 | 応答がない場合に処理が進めなくならないか。必要な打ち切りや中断ができるか | 応答待ちで停止処理まで止まる、失敗時の再試行でCPUを使い続ける |
| 失敗後の状態・出力 | 処理途中の失敗を検出し、状態や出力が矛盾しないか | 設定を一部だけ更新する、インストール漏れや処理失敗を成功として返す |
| 並行処理・終了 | 異常時にも、共有状態の更新、キャンセル、後片付けが整合するか | 終了後にコールバックが破棄済みのデータへ触れる、ロック待ちで終了できない |
| 復旧・再起動 | 再接続などの復旧条件を満たしてから再開し、古い状態を持ち越さないか | 通信が戻っただけで古い動作指令を再開する、再初期化で処理が二重登録される |
| 失敗の通知 | 呼び出し元や運用者が失敗を知り、原因を追えるか | 例外を握りつぶす、失敗したのに成功の戻り値を返す |

ログ、戻り値、例外、診断情報など、通知方法は対象の仕様に合わせます。
ログがあるだけで適切に対処できているとは判断せず、その後の状態・出力・利用側の動作も確認します。
関連するテストが、見つけた異常条件と期待動作を確認できるかも調べます。
テストがないことだけを、動作の不具合と同じ扱いにはしません。

## 指摘をまとめる

指摘には「発生条件 → 実際に通る処理 → 仕様との差 → 影響」が分かる根拠を付けます。
実行していなくてもコードから問題を確かめられる場合は、読み取った根拠と未実施のテストを示します。

他のレビューですでに報告された問題は、根拠を確認したうえで既存の指摘へまとめます。
同じ内容を別の問題として数えません。別レビューの結果が見られない場合は、未照合と記載します。

優先度は、起こり得る被害と発生条件を根拠に選びます。
エラー処理の問題であることだけを理由に、最高の優先度にはしません。

| 優先度 | 目安 |
| --- | --- |
| P0：緊急 | 広く避けられない条件で重大な被害や動作不能を招き、直ちに対応が必要 |
| P1：高 | 想定される使用条件で重大な不正動作や機能停止を招き、優先して修正が必要 |
| P2：中 | 特定の条件で誤動作し、修正が必要 |
| P3：低 | 影響が限定的な問題で、対応の優先度は低い |

仕様不足による確認事項や、好みによる改善案を、この優先度で不具合として数えません。
この目安は専用レビューの報告用です。既存サービスの投稿基準や、マージを止める設定を変更するものではありません。

## 報告形式

最初に「何を確認できたか」と「何が残っているか」を短く伝え、その後に次の順で記載します。
指摘が0件でも、確認範囲と未確認事項を残します。確認できなかった結果を「問題なし」としません。

### 対象と確認範囲

- 対象リポジトリ、PR番号やURL、比較元・比較先のコミット。未コミット変更を含む場合はその範囲。
- 参照した規約の版。配布済みの規約なら`SOURCE.json`の原本コミット、ローカルの変更を含むならその旨。
- 関連する仕様・設定・利用側と、確認できなかった資料。

確認項目の表にある観点ごとに、次の形式で記録します。

| 観点 | 確認状況 | 根拠・残っていること |
| --- | --- | --- |
| 入力・設定などの観点名 | 確認済み／未確認／対象外 | 読んだ処理やテスト、確認できない理由、または対象外の理由 |

「確認済み」は記載した範囲を調べた意味です。コードを読んだだけか、テストも実行したかを区別します。
一部しか確認できない観点は「未確認」とし、確認できた範囲と残りを併記します。

### 指摘

指摘ごとに、次の項目をまとめます。

```markdown
### [P1] 問題と対応が分かる短い見出し

- 場所：対象ファイルと行番号。
- 発生条件：どの入力・状態・操作で起きるか。
- 期待する動作と根拠：仕様・規約・利用側の契約など。
- 実際の動作と影響：コードが何を行い、どこへ影響するか。
- 修正方針：仕様に沿って、どの処理をどう直すか。
- 検証：コードで確認した根拠、実行したテストと結果、未実施の確認。
```

例えば「指令が期限切れになったら停止要求へ移る」という仕様がある処理では、
「通信が切れた場合が心配です」だけでなく、次のように説明します。実際の指摘ではない説明用の例です。

> 指令の受信が途絶えた際、今回の変更で停止要求を出す処理が呼ばれなくなっています。
> 直前に移動指令を受け取っていた場合、前回の指令が保持され、仕様の停止条件を満たせません。
> 期限切れを検出した分岐から停止要求へ移る処理を戻し、受信が途絶える条件をテストしてください。
> これはコードを読んで確認した内容で、実機の停止動作は未確認です。

実際の報告には、対象ファイル・行番号と仕様の参照先も付けます。

### 判断に必要な情報

仕様や資料が足りない場合は、対象箇所、分からない条件、その条件が判断に必要な理由を記載します。
不具合の件数とは分け、確認事項がなければ「なし」と記載します。

### 検証結果と未確認事項

実施した検査・テストと結果、未実施の項目と理由を、[testing.md](testing.md)に従って記載します。
必要なコードや差分を取得できない場合、またはレビューが途中で終了した場合は、その範囲が未確認であると明記します。

最終的なマージ判断や実機での安全性の確認まで完了した、という報告にはしません。
